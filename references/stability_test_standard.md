# OpenRouter 免费模型「推理级稳定性」测试标准

> 配套脚本：`scripts/inference_stability_test.py`
> 修订背景：原有 skill 仅用 OpenRouter 路由层的 `uptime_last_1d` 作稳定性代理，
> **无法捕获「爆满（capacity-full / 429·503）」与「中断（interruption / 超时 / 流截断）」**——
> 而这两类正是免费模型真实使用中的主导故障模式。实测校准结论（模型名取自 OpenRouter 公开目录，可自行复核）：
> - `thinkingmachines/inkling:free` —— 推理不稳定，经常爆满、中断。
> - `nvidia/nemotron-3-ultra-550b-a55b:free` —— 推理不稳定，经常爆满、中断。
> 二者端点在线率均 ≥96%，却被真实使用打脸。故推荐必须**以真实推理探测为终审**，端点在线率降为预筛。
> 历史校准基线：某款已下线的免费模型表现稳定、推理性能过关，**这类（稳定且会推理）才是值得推荐的**。
> （注：该模型当前不在 OpenRouter 目录内，仅作行为参照，不对它本身跑分。）

---

## 1. 为什么要另立此标准
| 信号 | 端点在线率代理 | 真实推理探测 |
|------|----------------|--------------|
| 托管可用性（厂商宕机） | ✅ 能反映 | ✅ 能反映 |
| **爆满 / 429·503（容量不足）** | ❌ 几乎不反映 | ✅ 直接测得 |
| **流中断 / 超时 / 截断** | ❌ 不反映 | ✅ 直接测得 |
| 真实首字时延 TTFT | ❌ 免费层不发布 | ✅ 测得 |
| 输出有效性（finish=stop） | ❌ | ✅ 测得 |
| **推理正确率（逻辑题）** | ❌ | ✅ 测得 |

结论：**端点在线率高 ≠ 真实可用**。本标准是推荐的硬性终审闸门。

## 2. 测试指标定义与观测口径（**同一批调用，多口径观测**）

> **核心方法（明示）**：所有指标来自**同一批真实调用**，**不为每个指标单独发请求**。
> 差别只在**观测口径**——同一批调用里：稳定性指标看「这次成了没有、怎么失败的」；
> 速度指标看「多久出第一个字、出多快」；推理指标只看其中 3 道推理题的**答案对错**；
> 完整性指标看 `finish_reason`。所以 12 次调用即可同时产出全部指标。

### 2.1 指标 → 观测口径对照表

| 指标 | 通俗解释（它回答什么问题） | 观测方法（怎么算出来的） | 取自哪些调用 |
|---|---|---|---|
| **成功率** `success_rate` | 发出去的请求，有多大比例真拿到了可用回答？ | 状态 200、无中断、未被拦截、`finish∈{stop, tool_calls, length}`、内容非空 | 全部有效调用 |
| **爆满率** `capacity_full_rate` | 有多大比例是被上游容量不足**直接拒绝**？你体感的"爆满"就是它 | 429 带 `provider_code`；503；错误体含 unavailable / upstream / overload / ResourceExhausted；或已发 200 但流中 `finish_reason:"error"` | 全部有效调用 |
| **中断率** `interrupt_rate` | 有多大比例是**已经开始出字却中途断掉**？（与爆满的"未开始就被拒"区分） | 连接重置 / 流截断 / 读超时 / 首 token 后 5xx / 无 `finish_reason` 就结束 | 全部有效调用 |
| **超时率** `timeout_rate` | 有多大比例慢到不可用？ | TTFT > 30s 或总时长 > 120s | 全部有效调用 |
| **首字时延** `ttft_p50 / ttft_p95` | 多久开始出第一个字？（越快越跟手） | 从发请求到收到首个内容片段的时间，取中位数与 P95 | 仅成功调用 |
| **总时延** `total_median_ms` | 一个请求从发到收完要多久？ | 请求发起至流结束的时长中位数 | 仅成功调用 |
| **输出速度** `throughput_cps` | 出字有多快？（同等 TTFT 下，出字慢会拖长等待） | 输出字符数 ÷ 总时长（字符/秒，取中位数） | 仅成功调用 |
| **完整输出率** `output_validity` | 有多大比例是**完整说完**而非被截断？ | `finish_reason == "stop"` 的比例 | 全部有效调用 |
| **截断率** `truncated_rate` | 有多大比例撞到输出上限被切？（撞上限≠不可用，仅影响完整度） | `finish_reason == "length"` 的比例，**不计入失败** | 全部有效调用 |
| **推理正确率** `reasoning_correct_rate` | 它**会不会思考**？还是只会流畅地胡说？ | 3 道推理题的答案正误比例（见 §2.2） | 仅 L1/L2/L3 调用 |
| **峰谷差异** `peak_risk` | 是不是只在高峰期才崩？（均值会掩盖这个风险） | 两窗口爆满率之差 > 10 个百分点即打标 | 跨阶段合并 |

> **判定优先级**：推理正确率 < 90% → 即便 100% 不爆满也直接判 D。
> 「能用」不等于「好用」；稳定但不推理的模型不值得推荐（须同时满足稳定与会推理）。

### 2.2 三道推理题（推理能力的观测载体）
| 编号 | 题目 | 唯一正解 | 判定方法 |
|---|---|---|---|
| L1 | All Bloops are Razzies. All Razzies are Lazzies. Are all Bloops definitely Lazzies? | **yes**（三段论传递） | 取回答中最先出现的 yes/no |
| L2 | A bat and a ball cost $1.10 total. The bat costs $1.00 more than the ball. How much is the ball? | **$0.05**（经典陷阱题） | 含 `0.05` / `5 cent` 且未答 `0.10` |
| L3 | All cats are animals. Some animals are black. Does it follow that some cats are black? | **no**（不能逆推） | 取回答中最先出现的 yes/no |

> 判定取**最先出现的答案词**，因为模型通常"先给答案再解释"，只看首个词可避免被后续解释干扰。

## 3. 测试协议（两阶段 · 择时 · 省配额）
账号有每日次数限制，故**不追求大样本**，采用「初筛 → 复筛」两阶段，把次数集中用在值得的模型上。

- **样本量**：阶段一 **12 次/模型**；阶段二 **18 次/模型**（幸存者合并 **n=30**）。依据见 §7。
- **批次轮转（指标同批）**：每轮按 `T1 → L1 → T2 → L2 → T3 → L3` 循环分配提示词。
  12 次 → 六档各 2 次；18 次 → 六档各 3 次。
  使一批调用同时覆盖：轻量可用性(T1) + 推理×3(L1/L2/L3) + 代码容量(T2) + 长文重载(T3)。
  爆满/中断/速度/推理/完整性全部在**同一次批次**产出，无需分指标单独跑。

| 提示档 | 内容 | 主要测得 |
|--------|------|----------|
| T1 轻量 | 一句定义短答（≤50 token） | 纯可用性 · 基础 TTFT |
| L1 逻辑 | 三段论传递（yes） | 推理正确率 |
| T2 代码 | 迭代版斐波那契（≈150–300 token） | 持续容量 · 中断 |
| L2 推理 | 球棒与球陷阱题（$0.05） | 推理正确率 |
| L3 逻辑 | 不可逆推的四段论（no） | 推理正确率 |
| T3 长文 | 500 字 Transformer 注意力长文（≈500+ token） | 负载下容量（最易爆满）· 超时 |

- **并发**：默认顺序（并发=1）测"单用户真实体感"；可选 `--concurrency K` 测突发。
- **真实重试**：对 success 指标**不做自动重试**（重试掩盖故障）；平台自身限流(无 provider_code)才退避重试，且不计入模型不稳定。

### 3.1 两阶段流程
- **阶段一 初筛（--phase 1）**：对全部候选模型发 12 次（单窗口，如低谷）。产出初筛评级。
  **排除闸门**：若触发任一项即刻排除，不再进入复筛（省配额）：
  - 爆满率 > 20%，**或**
  - 成功率 < 75%，**或**
  - 中断率 > 30%，**或**
  - 逻辑正确率（有样本时）< 50%（答不对题即不推荐）。
  > 无论该阶段落在峰或谷，只要触发阈值即排除——即用户要求的"无论峰谷，触阈值即排除"。
- **阶段二 复筛（--phase 2）**：仅对**初筛通过**的模型，在**另一个窗口**再发 18 次，
  与初筛间隔 **≥30 分钟（建议 1 小时）** 以形成可辨的峰谷区分（不作严格时段判定，仅看明显间隔）。
  复筛与初筛调用合并，重算最终指标与评级，并标记 `peak_risk`（某窗口爆满率显著高于另一窗口）。
- **最终判定**：以两阶段合并样本评级；任一阶段触发排除阈值即判 D。最终"值得推荐"须 A/B 且非 D、无峰值爆满风险。

### 3.2 OpenRouter 免费层限额（官方，测试必须遵守）
免费 `:free` 模型有硬限额，测试设计必须服从，否则会把自己误判为"模型爆满"：
- **累计充值 < 10 美元**：20 次/分、50 次/天。
- **累计充值 ≥ 10 美元**：20 次/分、1000 次/天。（门槛是 **$10**，不是 $1；推荐全量扫描前先充值）
- **按累计充值额计算，非当前余额**：充过一次即长期有效，余额花完也不回退。
- **失败请求照样计入当日额度**：被限流或被拒绝的请求同样扣配额，因此未提额就全量扫描极易把自己的限流误判为模型爆满。
- **DDoS 保护**：Cloudflare 会拦截远超合理用量的突发。
- **爆满/限流的两种 429，必须区分**：
  - 上游 provider **at capacity** → 429 带 `error.metadata.provider_code`（或 503 overloaded）→ **计入"爆满率"（真实信号）**。
  - 平台**自身限流** → 429 无 `provider_code` → 本测试被打限，**不计入模型不稳定**，应退避重试（读 `Retry-After`）。
  - 流中限流 → 以 SSE `finish_reason:"error"` 到达（已发 200），按爆满/中断处理。
- **协议约束**：顺序调用、调用间隔 ≥1s（远低于 20/分）；单次运行总调用数 ≤ 当日剩余配额；有效样本 <10 时判"样本不足"，不评级。

## 4. 评级（对照历史稳定标杆）
| 等级 | 判定（全部满足） | 含义 |
|------|------------------|------|
| **A 值得推荐** | success≥98% · 爆满≤2% · 中断≤3% · ttft_p95≤15s · 输出有效≥95% · **逻辑正确≥90%** · 且 T2/T3 也通过 | 稳定且会推理 |
| **B 可用** | success≥90% · 爆满≤8% · 中断≤8% · ttft_p95≤30s | 基本稳定 |
| **C 勉强** | success≥75% · 爆满≤20% | 偶发爆满/中断 |
| **D 不推荐** | success<75% 或 爆满>20% 或 频繁中断 或 逻辑正确<50% | 同 Inkling / Nemotron 3 Ultra 实测 |

附加标记：**峰值爆满风险** —— 若高峰窗爆满率显著高于低谷窗（差 >10 个百分点），打此标（即便均值为 B）。
**样本不足**：有效样本（排除平台自身限流）< 10 时评"样本不足"，须补跑；平台自身限流(429 无 provider_code)不计入模型不稳定。
**逻辑正确率 <90% 直接判 D**（答不对题即不推荐）；<50% 在初筛即触发排除闸门。

### 4.5 无效测试消除（提升可信度）
目标：**最大程度增加有效测试、消除无效测试**。
1. **本机网络/代理故障隔离**：502 Bad Gateway / Tunnel connection failed / SSL UNEXPECTED_EOF /
   RemoteDisconnected 等属测试基础设施故障，非模型问题 → 标记 `network`，**自动重试 4 次（退避 1.5s）**，
   仍失败则从指标中**整体剔除**（不计入成功率/中断率、不进黑名单）。此前这类故障被误计为"中断"，
   曾污染 Nemotron 3 Ultra / Super 的 peak 结果。
2. **平台自身限流剔除**：429 无 `provider_code`（即本测试被打限）→ 退避重试并剔除，不计入模型不稳定。
3. **不可测早停**：首次调用即判定为账号/区域/guardrail/agentic 拦截 → 立即停止该模型后续调用，
   单次仅耗 1 次配额（此前会白跑满 10 次）。
4. **明显失败早停**：前 5 次有效调用若「全部爆满」或「零成功」→ 停止后续调用，把配额留给有效模型。
5. 报告须披露：总调用数 / 有效样本数 / 有效测试率 / 已剔除的网络故障与平台限流次数。

### 4.6 不可测分类与处置（实测结论）
| 类别 | 精简标签 | 可否解除 | 处置方案 |
|---|---|---|---|
| 403 区域锁（`region-blocked`） | 区域锁 | **否** | 提供方对请求来源地合规限制；实测换 `eu.openrouter.ai` 域仍 403，与护栏无关。只能排除或换模型，不建议改出口地区（违条款＋增加故障面）。 |
| 403 限 agentic（`agentic-only`） | 限agentic | **否** | 官方条款限定免费端点仅可在 agentic harness 中使用；实测加 `tools` 参数、改用 `/api/v1/responses` 均仍 403。须接入 openrouter.ai/apps 中的应用；直连脚本不可测。 |
| 404 护栏拦截（`guardrail-blocked`） | 护栏拦截 | **可（用户设置）** | workspace 护栏过滤提供方/数据策略。到 `https://openrouter.ai/workspaces/default/guardrails` 放开即可；若含 `allowed_data_regions`，需 Business/Enterprise 计划，或改走对应区域域。 |
| 无端点（`no-endpoints`） | 无端点 | 视情况 | 路由下无可用端点（下线/区域不可达），确认目录后重跑。 |

**不可测 = 无法判定稳定性**，故不计入任何指标、不进黑名单；报告中「原因」列给最精简标签，
「备注」列给完整处置方案。

## 5. 推荐闸门（修正 skill 逻辑）
- 模型获"值得推荐"**仅当**真实推理测试达 A/B（两阶段合并），**而非**仅凭高端点在线率。
- 原端点在线率排名降为「托管可靠性预筛」；与真实测试冲突时**以真实测试为准并显式标注背离**。
- 输出须含：每候选的 成功率 / 爆满率 / 中断率 / TTFT(P95) / 输出有效 / 逻辑正确 / 评级 / 峰值风险 / 初筛是否排除。

## 6. 执行
- **必需 `OPENROUTER_API_KEY`**（免费模型推理本身 $0，但仍需 Key 与配额）。无 Key 时 skill 必须声明"无法做真实推理测试"，仅给代理+本标准。
- 阶段一（全部候选，12 次/模型，单窗口）：
  ```bash
  export OPENROUTER_API_KEY=sk-or-...
  python inference_stability_test.py --phase 1 --from-classified free_models_classified.json --rounds 12 --window offpeak
  ```
- 间隔 ≥30 分钟（建议 1 小时）后，阶段二（仅复筛初筛通过者，另窗口，默认 18 次）：
  ```bash
  python inference_stability_test.py --phase 2 --window peak          # 默认 --rounds2 18
  python inference_stability_test.py --phase 2 --rounds2 24 --window peak   # 需要更高可信度时
  ```
  > `--phase 2` 自动读取阶段一产出的 `inference_stability.json`，只对未排除模型补测；
  > 也可用 `--models id1,id2` 只复筛指定几个（进一步省配额）。
- 产出：`inference_stability.json`（逐模型 两阶段调用明细 + 合并指标 + 95% 置信区间 + 评级 + 峰谷风险）+ 控制台摘要 + 图文报告。

## 7. 样本量与结论可信度（为什么是 12 / 18，而不是 10）

**统计依据**：比率型指标在小样本下必须用 **Wilson 95% 置信区间**，「零失败」时用 **3/n 法则**
（n 次零失败 → 可断言真实失败率 ≤ 3/n，95% 置信）。

| 样本 n | 零失败时可断言的失败率上界 | 观测成功率 90% 时的 95% CI | 能做什么 |
|---|---|---|---|
| 10 | ≤ 30% | 约 [60%, 98%] | 只能粗筛，**不足以支撑结论** |
| **12（阶段一）** | ≤ 25% | 约 [65%, 99%] | 检出**量级级**故障（爆满≥20%、成功率<75%），用于**淘汰** |
| **30（幸存者合并）** | ≤ 10% | 约 [74%, 97%] | 可给出**相对可信**的稳定性结论与区间 |
| 60 | ≤ 5% | 约 [80%, 95%] | 接近确认「基本稳定」 |
| 150 | ≤ 2% | 约 [85%, 94%] | 才够**证实 A 级**（失败率≤2%），单模型成本过高 |

**结论（诚实边界）**：
1. **n=10 不具备独立支撑结论的可信度**（区间宽达 38 个百分点），故提升至阶段一 12、幸存者合并 30。
2. **不能**用可行样本证实 A 级所需的「失败率 ≤2%」——那需要 n≈150 且零失败。
   因此 **A 级必须标注「未达证实门槛」**；若零失败但 n<150，只可断言"真实失败率 ≤ 3/n"。
3. 样本**不宜再高**：n>60 后区间收窄变慢（边际收益递减），却显著拉长测试时长、增加被上游限流的风险。
   故采用**淘汰用 12、结论用 30** 的两级设计，把样本花在值得的模型上。
4. 报告**必须显示 95% CI 与最坏情况失败率上界**，不得只报点估计。

## 8. 结果展示要求

> **两阶段各出一份独立报告，互不混合**：阶段一 → `phase1_report.html`；阶段二 → `phase2_report.html`。
> 另有一份**过程页**（实时看板）`phase1_live.html`，仅反映测试进行中的状态，不作为结论。

### 8.1 首轮（阶段一）——**快览**
目标：让用户在**几十秒内**形成初步判断，并看清谁值得进复筛。
- 一屏内展示**全部候选**的一行结论：模型 / 评级 / 成功率 / 爆满 / 中断 / TTFT / 推理 / 样本 / 备注。
- **不设「原因」列**：原因、处置与样本说明全部并入**备注列**（避免一列短语 + 一列长文的冗余，也利于压行高）。
- 排序：**可用置顶、淘汰居中、不可测沉底**——有限视野里先看到有效信息。
- 顶部快览卡片：候选数 / 通过 / 淘汰 / 不可测 / 有效测试率。
- 不展开置信区间与分项，只给"初步结论 + 是否进复筛"。
- **模糊结论必须问题锚定（硬规则）**：
  - **被闸门淘汰（初筛早停）**：指标栏（成功率/爆满/中断/TTFT/推理/样本）**统一显示「已被淘汰」**，
    不显示「样本不足」。备注栏附实测数值（成功率/爆满率/中断率 + 有效样本数）做问题锚定——
    证据已足：前 5 次有效调用全爆满/零成功，样本少是"主动停批省配额"导致，非随机缺失。
  - **不可测**：评级显示为「不可测」，并在行内/备注给出**具体原因简写**，不得只写"不可测"。
    简写映射：`region-blocked→区域锁（来源地合规限制）`、`agentic-only→只能 agentic 调用`、
    `guardrail-blocked→护栏拦截`、`no-endpoints→无可用端点`；未知拦截→"账号/平台侧拦截"。
  - **样本不足**：仅留给"通过闸门但 n_eff<10"的少数情形；备注须附实测样本数锚定（如"样本仅 N"）。

### 8.2 终轮（阶段二）——**相对可信的结论**
目标：给出可据此选型的结果。
- 仅展示幸存者，含**两阶段合并样本 n**、**95% CI**、**最坏情况失败率上界**、峰谷对比、
  速度（TTFT P50/P95 + 输出速度）、推理分项（L1/L2/L3 各题正确率）、最终评级与推荐结论。
- 明确标注可信度边界（如 A 级"未达证实门槛"）。

### 8.3 实时看板（阶段一过程页）
- **拿到免费名单后框架即生成**：先渲染全部候选为「待测」行，再随测试推进逐行更新。
- 每完成一次调用即重写页面（写入限流：最快每 2s 一次）；页面自带 3s 自动刷新。
- 每行显示：状态（待测/测试中/完成·淘汰/不可测）、进度（已测/总次数）、成功/爆满/中断计数、
  有效样本、最近 TTFT、推理对错数；正在测的行高亮。
- 顶部：总体进度条、已测完模型数、剩余 ETA、累计调用与剔除计数。
- 阶段一结束即定格（刷新间隔放宽，标注"已结束"）。

### 8.4 行高规则（**规则，不是死值**）
目标：既要保留充分的解释说明，又不让行高过高影响一屏展示量。
- **备注列宽占比大（约 55–58%）＋ 字号略小 ＋ 行高 1.4**：把原「原因」列的空间让给备注，
  让完整解释在更宽的容器里自然落在 2–3 行内，而不是靠截断文字来压行高。
- 其余列（评级/数值）**单行不换行**，避免纵向膨胀。
- 不可测行的原因用最精简标签（区域锁 / 限agentic / 护栏拦截 / 无端点）作为备注列前缀，完整方案紧随其后。
- 判定标准：**解释不删减，行高靠"加宽容器"而非"砍内容"来控制。**
